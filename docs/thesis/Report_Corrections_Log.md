**C7. Gyro prior (SWI), what it is and whether it could help F26 (answered 11 Nov, nothing run).** `gyro_prior.py` integrates the gyro between the last finished scan and the current one (zero-order hold), converts it to the LiDAR frame with the extrinsic rotation, and replaces only the ROTATION of the LiDAR increment used as the starting guess; the translation stays A-LOAM's scan-to-scan translation. No bias estimate, no accelerometer, no preintegration. Evidence (replica doc, sections 12 to 17): Multi Floor SW 5.03 / 5.44 against SWI 1.51 (n=1, not repeated, designed after the SW result on that bag); Long Corridor SW 12.58 / 13.12 against SWI 13.81 / 13.24 (no help). Median gyro-versus-A-LOAM rotation difference 0.65 to 0.70 deg per scan, large for a 0.1 s scan, cause not examined (bias, time offset or A-LOAM error). It is not in F26: `fusion_node_v2.py` uses the gyro only for the standstill detector (ZUPT), and F26's guess comes from `guess_status.py` (A-LOAM increment, Eq. 13 blend or VINS step). Expectation, a hypothesis only: little to modest gain at best. In F26 the output rotation already comes from VINS-Mono, and the guess matters where it is A-LOAM's own increment (98 % of scans on Corridor02). The Multi Floor gain was seen where A-LOAM was the output and its guess was the only rotation source (SW 5.03 against F26 0.54). Cave02 and GEODE errors are offsets between segments, vertical drift on the stairs and a translation stall (Cave02 285 to 305 s), which a rotation prior does not address directly. Adding it to F26 would be a new version made after seeing development data, so it needs new code in the guess module, a rule written first, live runs (A-LOAM's input changes, so a replay of logs cannot test it) and a held-out bag. Suggested use in the report: at most one line under future work (a gyro rotation prior for A-LOAM's guess, untested in F26). OPEN: owner to decide whether that line goes in.
