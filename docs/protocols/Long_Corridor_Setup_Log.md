# Long Corridor: what the downloaded files turned out to be

*15 October 2026. Everything below was read from the files on the user's machine (command output pasted into the session), except where marked.*

## Bag (`raw_data_core_2023-07-25-03-01-44.bag`, 6.1 GB, from `SubT_MRS_Hawkins_Long_Corridor_RC.zip`)
- Duration 279 s (280.0 s from first to last message); 65,454 messages.
- `/camera_1/image_raw` 6720 msgs (about 24 Hz), `/imu/data` 55,957 msgs (about 200 Hz), `/velodyne_packets` 2777 msgs (about 10 Hz, `velodyne_msgs/VelodyneScan`). No PointCloud2 topic: the Velodyne packet conversion launch is needed, as in Multi Floor.
- Camera model from the intrinsics file: MEI, 640×480; camera-to-IMU translation (0.180, 0.047, -0.020) m. VINS-Mono config generated by `make_vins_config.py` (IMU noise and tracker settings copied from Multi Floor, nothing tuned).

## Ground truth `corridor01_gt.txt` (SuperLoc release)
- TUM format, 1385 poses at 5.0 Hz, 279.2 s, path 579.2 m (the web pages quote 616–617 m; the 5 Hz sampling shortens a path), starts at the origin (0, 0, 0) and ends at (-2.93, 1.52, 0.29): a loop.
- Time span 1517157219.79 .. 1517157498.96: **on the header clock**, so it overlaps the logs directly. It starts 0.6 s after the first mapped scan. No time shift is needed. (An early setup check compared it with the record times and wrongly reported NO OVERLAP; fixed.)
- The same download folder also held `floor01_gt.txt` (the Multi Floor GT, 175 KB) and an apparently empty `Multi-Modal-Sensor-Fusion-Track` folder; the challenge release was not inspected.

## Smoke test (70 s of the bag, F8, C_T = 0.03, nothing tuned)
- 693 log rows in 70 s; VINS-Mono present from 1.3 s (680 rows); Hessian in 692 rows; 211 WARMUP rows then FUSED (first at 21.4 s).
- Scored against `corridor01_gt.txt` with no shift: 687 of 693 poses inside the GT span, RMSE 1.07 m, max 1.70 m on this first 70 s (about 140 m), which is not the full-run number. Residual time offset to be checked with `align_gt_time.py --check-only` on a full run.

## Bugs found on first real use
1. `setup_sequence.sh` picked the message type `velodyne_msgs/VelodyneScan` instead of the topic `/velodyne_packets` (the `types:` lines of `rosbag info` also matched, and a locale-dependent sort put them first). Fixed: only topic lines match, and the script stops if a message type was chosen.
2. The ground-truth check compared against record times; the nodes use header stamps. Fixed: setup reads the first header stamps from the bag.

## Time-alignment tool (kept for sequences whose GT is on another clock)
`align_gt_time.py` decides the shift from the correlation of the rotation speed of the GT with that of VINS-Mono and A-LOAM rotations (independent of the fused output, frame and drift); cross-check by ATE-minimising offsets; refuses to write if sources disagree by more than 0.3 s. Self-tests on Multi Floor: GT moved by +4.00 s -> +4.00 / +4.02 s; GT already aligned -> +0.01 s. A first design that decided the shift from VINS positions was biased by 0.37 s (drift) and was dropped.

# Long Corridor results (15 October 2026), settings frozen from Multi Floor (C_T = 0.03, nothing tuned)

## Live runs, ATE RMSE in metres, 3 runs each
| Config | Runs | Mean ± sd |
|---|---|---|
| F8 ours (soft Schur translation weight, rotation from VINS) | 4.76, 4.87, 3.97 | 4.53 ± 0.49 |
| F12 hard switch, Switch-SLAM detection rule | 6.05, 4.65, 5.58 | 5.43 ± 0.71 |
| F0 VINS-Mono alone | 5.66, 6.13, 5.65 | 5.81 ± 0.28 |
| F14 LiDAR translation always (W = I) | 9.97, 23.11, 6.56 | 13.2 ± 8.7 |
| F5 A-LOAM alone, no VINS prediction | 23.0, 13.2, 11.2 | 15.8 ± 6.3 |

With the loop-closure back end (iso loop weights, one search round, odometry noise 1.46° / 0.054 m frozen from Multi Floor), F8 recordings: 4.76 → 2.91, 4.87 → 3.26, 3.97 → 1.85 (mean 4.53 → 2.67 ± 0.73, 3/3 improve; max errors 9.15, 10.52, 5.95 m). Published: Switch-SLAM 2.42 (max 5.09) without loop closure, ICCV'23 challenge best 1.254, LODESTAR 1.386 (threshold grid-searched on this sequence). **Not below the published numbers.** Multi Floor remains 0.347 ± 0.036 m.

## Diagnosis (from the logs, no ground truth needed)
The route is a loop: GT start-to-end distance 3.32 m.
| Trajectory | start-to-end distance |
|---|---|
| VINS-Mono | 24–26 m |
| our fused pose (F8) | 21–25 m |
| A-LOAM scan-to-map pose, logged but not output (F8 runs) | 2.8, 4.1, 3.9 m |
Fused path length (597–599 m) matches the A-LOAM path (602–605 m), VINS is 580 m: translations come from the LiDAR, the heading from VINS. VINS-versus-LiDAR relative rotation grows to about 10° by 250 s (a slow, steady drift). Replay of the logged A-LOAM poses as a LiDAR-only trajectory: ATE 2.61, 1.04, 1.09 m on the F8 logs and 1.40, 0.68, 2.12 on the F0 logs, versus 4.76, 4.87, 3.97 for the fused output. So on this sequence the VINS-seeded LiDAR map pose is better than our fused pose; on Multi Floor it is the reverse (LiDAR-only replay 2.05 m versus 0.63 m fused; live F4 7.75).

## Offline replay tests of remedies (6 Multi Floor logs with GT, 6 corridor logs; corridor measured by loop gap, true 3.3 m)
| Remedy | Multi Floor full ATE | Corridor loop gap |
|---|---|---|
| none (ours) | 0.626 | 23.7 m |
| constant LiDAR rotation weight C_R = 1e-3 / 1e-2 / 1e-1 | 1.07 / 1.60 / 1.93 | 13.8 / 9.1 / 8.3 |
| rotation fully from LiDAR (C_T 0.3) | 2.05 | 5.4 |
| slow drift filter on all rotation axes, τ = 300 s | 0.81 | 14.6 |
| same, yaw (gravity axis) only, τ = 300 s | 0.71 | 15.0 |
| yaw only with clipped (bounded-influence) innovations | 0.625–0.686 | 21–23 |
No remedy that is safe on Multi Floor helps the corridor, and none that helps the corridor is safe on Multi Floor. In Multi Floor the fused path itself strays up to 10–13 m from the A-LOAM map pose in the middle of a run (stairs), so a trust region calibrated on Multi Floor cannot bound the corridor's drift (3–4 % of path). The Schur information of the rotation block explains the LiDAR rotation error only weakly (Spearman about 0.3–0.5 on Multi Floor windows).

## Back end limits seen
All 52–57 loops connect the same place (about 120 s ↔ 155 s); the start/end loop (20+ m apart in the front-end estimate) is never considered because the search radius is 8 m and ICP verification accepts corrections up to 4 m / 15° only. Widening the radius alone cannot work.

## Consequence for the study design
A rule was being looked for after seeing Long Corridor results, so **Long Corridor is a development sequence from now on**. The untouched test set is Corridor02 (RC1, Hawkins, 893 s, 690 m) and any other sequence not yet used. Everything in the "frozen settings" claim holds for the numbers above (they were produced before any change).

## Honest reading
- Strength confirmed: soft information weighting beats the hard switch and the always-LiDAR variant on a degenerate-prone corridor, and is far more stable (sd 0.49 versus 8.7 for always-LiDAR).
- Weakness found: the VIO-primary design inherits VINS-Mono's heading drift on a 580 m low-parallax corridor; the architecture (rotation from VIO) cannot undo it; LiDAR-led pose estimation is better there and worse on Multi Floor. No single fixed choice of leading sensor worked on both; a selection rule based on observable VIO health has not been found yet.
